# 知识库 / 牌组 / 卡牌设计手册

## 1. 三层结构的职责

```text
知识库 KnowledgeBase  →  一个连贯的学习领域
  牌组 Deck            →  章节 / 主题 / 技能模块
    卡牌 Card          →  一个可独立回忆的原子知识点
```

- **知识库**回答「我在学什么」。
- **牌组**回答「这一块属于哪个章节/主题」。
- **卡牌**回答「我具体要记住哪一个点」。

不要把「知识库」当成文件夹、把「牌组」当成页码。结构应反映知识本身的组织方式。

## 2. 知识库设计

### 一个知识库 = 一个学习领域

合适的知识库：

- 「西班牙语 A1 核心」
- 「计算机网络基础」
- 「刑事诉讼法」
- 「产品经理面试题库」
- 「《人类简史》核心观点」

不合适：

- 「我的知识库」「杂项」「其他」——没有学习边界
- 把一整本书拆成 20 个知识库——层级过深，复习时无法跨章节混合
- 把多个不相关学科塞进一个知识库——牌组会失去意义

### 命名

- 具体、可识别：`科目 + 范围/级别`。
- 中文 4–16 字；英文 2–6 个词。
- 不要用日期、版本号做名字（版本放在文件名或描述里）。
- `description` 一句话说明「学完能掌握什么」，不要写「这是知识库」。

### 图标

从内置风格中选一个：`📁 🗂️ 📚 🧠 🌍 🔬 🎨 💡`。同一用户的知识库尽量不重复太多。

### 多份文档怎么处理

- **同一主题的多份材料** → 一个知识库，按文档/章节建牌组，用标签记录来源。
- **不同主题** → 不同知识库。
- 不要把同一知识点的多个来源做成多张重复卡；合并成一张，选取最清晰的表述。

## 3. 牌组设计

### 按「概念簇」而不是「页数」拆

好的牌组边界：

- 一个章节的核心概念
- 一类技能/题型
- 一个对比主题（如「TCP vs UDP」）
- 一个流程/系统（如「HTTP 请求生命周期」）
- 一组同质词汇（如「餐厅用语」「学术动词」）

坏的边界：

- 「第 1–10 页」「PPT 上半部分」
- 「简单」「困难」——难度不是知识结构
- 每 5 张卡一个牌组——过碎

### 规模

| 规模 | 建议 |
|---|---|
| < 5 张 | 太小，考虑并入相邻牌组 |
| 20–60 张 | 理想 |
| 60–80 张 | 可接受，观察是否主题过杂 |
| > 80 张 | 考虑拆分 |
| > 150 张 | 必须拆分 |

拆分依据是**主题边界**，不是平均切分。

### 命名与描述

- 名称：2–12 字，名词短语。例：「时态与语态」「动态规划」「 WWII 战役」。
- 描述：一句话说明范围。例：「英语六大时态的构成与使用场景」。
- 颜色：同知识库内可用同色系或按主题区分；不要每张牌组都换色。
- 图标：与主题相关；同一知识库内风格统一。

### 嵌套牌组

`parentId` 支持两层结构，适合：

- 大科目 → 章节（如「计算机网络」→「传输层」）
- 语言 → 技能（如「日语 N5」→「语法」「词汇」）

不建议超过两层；三层以上在移动端难以浏览。父牌组必须先于子牌组出现在 JSON 中。

## 4. 卡牌设计：原子化

### 一张卡只考一个点

判断方法：**如果学习者答对了一半，这张卡应该算对还是算错？**

- 算不清楚 → 说明一张卡里有多個独立考点 → 拆。
- 例：「TCP 三次握手的过程、作用和缺点」→ 拆成「过程」「目的」「为什么不是两次」等。
- 例：「React 的 useState 和 useEffect 有什么区别」→ 拆成「useState 的作用」「useEffect 的作用」「两者区别」或改成选择题。

### 正面必须自足

- 不用代词开头（「它有什么作用？」——「它」指什么？）。
- 不依赖上一张卡的上下文。
- 不依赖图片（当前学习界面不渲染媒体）。
- 不依赖「如上所述」「根据原文」。
- 包含必要的限定范围（如「在 Kotlin 中」「根据《民法典》」）。

### 背面直接给答案

- 第一句就是答案，不要先铺垫。
- 最多补一句解释或一个例子。
- 列表超过 4 项 → 拆分或改 `MARKDOWN` 速查卡。
- 不要在背面写「见教材第 3 章」——复习时看不到教材。

### 难度分层

一个牌组内自然包含：

- **基础层**：定义、术语、事实（占 40–50%）
- **核心层**：原理、因果、对比、流程（占 30–40%）
- **应用层**：案例判断、易错点、边界条件（占 10–20%）

不要全部停留在「什么是 X」；也不要一上来全是综合题。

## 5. 从文档抽取卡片的方法

### 三遍法

**第一遍：结构**

- 读标题、目录、摘要、结论。
- 列出「章节 → 核心主题」。
- 决定知识库和牌组边界。

**第二遍：概念**

- 标记定义、术语、公式、分类、步骤、对比、数字、人物、事件。
- 每个标记问：这是「需要记住」还是「只需理解」？
- 只把需要**主动回忆**的内容做成卡；纯背景叙述不做卡。

**第三遍：关系**

- 因果：为什么？导致什么？
- 对比：A 与 B 的区别？各自适用场景？
- 条件：什么情况下成立？例外是什么？
- 应用：给一个例子，能否判断？

### 覆盖率与数量

- 优先覆盖「删掉它，这一章就理解不了」的核心概念（通常占材料 20–30%）。
- 不要把每一句话都做成卡；解释性段落通常提炼成 1–2 张卡。
- 经验密度：
  - 概念型教材：每 1–2 段核心内容 1 张卡
  - 语言词汇：每词 1 张（双向则 2 张）
  - 代码文档：每个概念/API 1 张 + 每个易错点 1 张
  - 历史叙事：每个关键事件/人物/因果 1 张
  - 法律/医学：每个构成要件/诊断标准 1 张，措辞必须精确
- 宁少勿滥：30 张能覆盖核心的卡，优于 100 张复读卡。
- 如果用户明确要求「尽可能全面」，可以提高覆盖，但仍保持一卡一点。

### 不要做成卡的内容

- 纯过渡句、目录、致谢、广告
- 需要整段背诵才有意义的文字（除非拆成 Cloze 关键句）
- 依赖图片/图表的空间关系（当前不支持媒体渲染）
- 过于依赖上下文的玩笑、隐喻、文学赏析（可改为「作者为什么用这个意象」的 BASIC 卡）
- 有争议、答案不唯一、需要长篇限定条件的内容

## 6. 标题与标签

### 标题（title）

- 4–16 个汉字，或 2–8 个英文词。
- 是「概念名」而不是「问题复述」。
- 同一牌组内标题不重复；相同概念的不同侧面用后缀区分（如「TCP 三次握手 · 目的」）。
- 作用：列表识别、搜索、排序；学习页不显示标题，但管理时很重要。

好的标题：

- 「机会成本」
- 「TCP 三次握手的目的」
- 「虚拟语气 · 与过去事实相反」
- 「二分查找边界条件」

坏的标题：

- 「什么是机会成本？」（复述问题）
- 「第一张」「card 001」（无信息）
- 一整句话（过长）

### 标签（tags）

- 1–4 个，风格统一。
- 推荐分层：`章节::主题`、`类型::定义`、`难度::基础`、`来源::教材名`。
- 不要用空格分隔的句子；用简短名词。
- 同一知识库内复用标签，不要为每张卡发明新标签。
- 示例：

```json
"tags": ["第三章::动态规划", "类型::方法", "难度::进阶"]
```

- 标签语言与卡片内容一致；技术术语保留原文。

## 7. 不同材料类型的策略

### 概念/理论型（教材、课程）

- 定义 → BASIC
- 关键术语 → CLOZE
- 原理/因果 → BASIC（为什么/如果……会怎样）
- 对比 → MULTIPLE_CHOICE 或 MARKDOWN 对比表 + BASIC 辨析卡
- 公式 → CLOZE 或 BASIC（纯公式居中）
- 章节总结 → MARKDOWN 速查卡（少量）

### 语言学习

- 单词 ↔ 释义 → BASIC（需要双向则两张）
- 例句中的语法点 → CLOZE
- 易混词（affect/effect、ser/estar）→ MULTIPLE_CHOICE
- 语法规则 → BASIC + 例句
- 变位/搭配 → CLOZE
- 发音/重音 → RICH_TEXT 标注（不用图片）
- 不要只做「单词表」；每个词至少给一个搭配或例句。

### 编程/技术

- 概念 → BASIC
- API/关键字/命令 → CLOZE 或 MARKDOWN
- 代码示例 → MARKDOWN 代码块
- 易错点/边界 → MULTIPLE_CHOICE 或 BASIC
- 对比（如 `==` vs `===`）→ MULTIPLE_CHOICE / MARKDOWN 表
- 保留原始标识符、大小写、路径、命令；不要翻译。

### 历史/人文

- 事件：时间、地点、人物、原因、结果 → 拆卡
- 因果链 → BASIC（为什么/导致了什么）
- 比较（两次改革、两位思想家）→ MARKDOWN 表 + 辨析选择题
- 时间线 → MARKDOWN（一条时间线一张卡，不要每个日期一张孤立卡）
- 文学：作者/作品/主题/手法 → BASIC；名句 → CLOZE（挖关键词，不挖整句）

### 法律/医学/金融等高风险领域

- 措辞必须与原文一致，不改写关键限定词。
- 构成要件/诊断标准 → CLOZE（挖关键条件）或 MARKDOWN 清单。
- 数字、期限、剂量 → BASIC，正面给情境，背面给精确值。
- 不做「以下哪个一定正确」这类需要大量背景的题，除非材料明确。
- 拿不准的内容不要生成；宁缺毋滥。

### 流程/SOP

- 整体流程 → MARKDOWN 有序列表（速查，不承担主要评分）
- 每个关键步骤/判断点 → BASIC
- 顺序易错 → MULTIPLE_CHOICE 或 CLOZE
- 例外/回退路径 → BASIC

## 8. 去重与合并

- 同一概念在多个章节出现：保留表述最清晰的一张，其他位置用标签关联。
- 同一张卡不要同时考「定义」和「例子」；拆成两张。
- 语义相同、只换措辞的卡：删掉一张。
- 正反向卡不算重复，但只在两个方向都值得练时保留。
- 相似度判断看「正面问的是不是同一件事」，而不是文字是否完全相同。

## 9. 生成前的覆盖计划（内部使用）

在写 JSON 前，先用一张表核对覆盖，不必交付给用户：

| 源章节 | 牌组 | 核心点 | 卡型 | 数量 |
|---|---|---|---|---|
| 第 1 章 | 基本概念 | 定义、术语、分类 | BASIC/CLOZE | 12 |
| 第 2 章 | 核心原理 | 因果、机制 | BASIC/MC | 15 |
| 第 3 章 | 应用 | 案例、边界 | MC/BASIC | 10 |

检查：

- 每个核心章节都有对应牌组吗？
- 每个牌组都有足够的「核心层」而不只是定义吗？
- 有没有整章遗漏？有没有同一知识点重复？
- 卡型分布是否合理？是否全是 BASIC？

## 10. 交付前质量清单

- [ ] 知识库边界清晰，名称具体。
- [ ] 牌组按主题划分，规模在 20–80 张之间。
- [ ] 每张卡只考一个点。
- [ ] 正面自足，不依赖上下文/图片/上一张卡。
- [ ] 背面第一句就是答案。
- [ ] 没有语义重复卡。
- [ ] 标题简短且不复述问题。
- [ ] 标签 1–4 个，风格统一，可复用。
- [ ] 卡型与知识特征匹配，不是全部 BASIC。
- [ ] 长内容没有被塞进一张卡。
- [ ] 代码/公式/术语保留原文。
